# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **The cashier sees the sales of their shift** — "Ventas del turno" in the POS menu lists the sales of the shift in progress (time, receipt number, payment methods, total, and whether the receipt was accepted, rejected or is pending at SUNAT), voided ones struck through and not counted, with a reprint action; it opens from the close dialog too, so a cashier whose count does not match can find the sale behind the difference. New `GET /api/cash-pos-state/sales` (`cash.view`) answers only for the signed-in user's own open session of the current branch, so no `sales.view` is needed: that permission opens the whole branch's sales. The close form now also shows how many operations stand behind each payment method (`operations` in the X report). The lookup of the user's open session is shared by `cash-pos-state` and this endpoint (`OpenCashSessionLocator`), so they cannot disagree about which shift is the shift. No schema change.
- **The cashier runs the whole shift from the POS** — "Abrir caja" asks for the opening cash (and which register, when the branch has several free), "Movimientos y reporte X" shows the partial cut and lets the cashier register cash in or out by hand (category, amount, description; needs `cash.movement`), and "Cerrar caja" counts the drawer and closes it in a dialog, with the same count, draft and confirmation as the full page (`/cash-session/:id/close`, now sharing one `CashCloseFlow`). New `GET /api/cash-pos-state` (`cash.view`) answers what the POS needs: the session the signed-in user has open, and the free registers of the branch. `cash_movement:read` now exposes `createdAt`. No schema change.
- **Offline sales are signed, so they belong to whoever made them** — while online, a cashier's till receives a credential (`POST /api/pos/offline-credential`, needs `pos.offline_sale`; valid 72 h, handed out again while more than 24 h remain, secret derived from the server key and never stored). A sale made without connection is signed at creation over the exact body that will be sent, and the server verifies the signature (`X-Offline-Credential`, `X-Offline-Signed-At`, `X-Offline-Signature`) before attributing the sale: seller, cash session, treasury movement and permissions are those of the person who signed, whoever's session delivers it, and `sales.synced_by_user_id` records who did. A signature that does not hold (altered body, another key, outside the credential's life, revoked before it) refuses the sale; a sale without signature (no Web Crypto, or queued before this) behaves as before. Signed sales no longer wait for their owner to sign in. Migration `Version20261122100000_offline_credentials` (`identity_offline_credential`, `sales.synced_by_user_id`).
- **Offline sales at a different price are accepted and listed for review** — a sale made without connection is never refused at sync because its price differs from the one in force (the customer already has the ticket; a cashier cannot change prices anyway, so the difference is almost always a till with an old catalogue). The line is recorded as `offline_diff` with the price the server expected, and listed in Facturación → "Precios a revisar" (`GET /api/sale-price-review`, needs `reports.view`): seller, document, charged vs current price, difference and effect. Online sales keep being refused when the price is not the current one and the user lacks `pos.price_override`.
- **Offline sales are sent by their owner** — a queued sale remembers who made it and is only sent from that person's session; the server attributes a sale (seller, cash movement, permissions) to whoever is signed in when it arrives, so on a shared till the next cashier used to send the previous one's sales as their own. The pending-sales panel says when some belong to someone else. Sales queued before this keep being sent by anyone.
- **Catalogue delta for the till** — `GET /api/products-changes?since=<cursor>` returns only the products changed since the till's last sync (same shape as `GET /api/products`) plus the cursor for the next call; without `since` it returns just a cursor. The POS now asks for the delta on every refresh and downloads the whole catalogue only the first time, after 30 minutes, or if the delta fails (deleted products leave no trace, so it reconciles in full). The cursor is the database's own clock, taken before reading and with a 10 s overlap so a write in flight is never lost. Needs migration `Version20261122000000_product_updated_at` (`producto.updated_at`, maintained by the database, indexed).
- **Price-list history and price source on sales** — saving a price list leaves a before/after entry per product in the list's "Historial de cambios" (same trail as products; written in the same transaction as the prices). Every sale line now records where its price came from (`catalog`, `price_list` or `manual`, decided by the server) and the price the server expected (`sale_items.price_source`, `list_price_snapshot`), so a sale at an outdated price shows as `manual` next to the current one. Migration `Version20261121190000_sale_item_price_source`; lines written before it have both empty.
- **Activity record (Ajustes → Actividad)** — a per-tenant, append-only record of who did what: sign-ins (with browser and system, and whether a second factor was used), failed sign-ins, invitations sent and accepted, second factor turned on / off / reset by an administrator, password recovery, role permission changes (what was added and removed, by label), and users created or removed. Entries flagged "Sensible" are the ones worth reviewing; routine sign-ins show under "Todos". Filters by user, type, day range and free text, a weekly summary, and a CSV export (UTF-8 BOM, formula-injection safe, capped at 5,000 rows). New `identity_activity_event` table and `activity.view` permission, granted to the administrator role by the migration (the super administrator has it implicitly). There is no API to edit or delete an entry, and the actor's name is stored with the entry so it survives the user being removed; the record never throws into the operation it observes, and failed sign-ins are capped at 10 per address per minute so the table cannot be flooded. Scope: only events that exist today — PIN approvals, cash drawer and price changes from the Figma design are not recorded yet.
- **Identity module (invitations, password recovery, 2FA)** — adopts the identity features of `nubitio/admin-bundle`, **off by default** (`IDENTITY_MODULE_ENABLED=0`; see `docs/operations/identity-module-rollout.md` for the mandatory rollout order). Administrators invite by e-mail with a role (`POST /api/user-invitations`; the token travels only in the mail), invitees choose their own password, users can recover a forgotten one, and each user may enable TOTP with recovery codes from the user menu. Nothing is forced: no role is required to use a second factor, and an abandoned enrolment does not affect sign-in. Adds `usuario.email` (unique, optional) and `usuario.last_login_at` (shown in the users grid), the `nubit_*` identity tables, `app:identity:preflight` (run before enabling: exits non-zero if any tenant lacks the tables) and `app:identity:totp-reset` / `DELETE /api/users/{id}/totp` to recover someone who lost their device. The flag lives in `config/packages/nubit_admin_identity.php` because the bundle reads it without resolving `%env()%`, which would enable it even when set to `0`.
- **Payables — 30-day outlook** — `GET /api/supplier-bills-forecast` and a "Próximos 30 días" panel on Cuentas por pagar: cash in open sessions + receivables due in the next 30 days − supplier payments due, in PEN. Bank balances are not included because statement imports hold no running balance.
- **Payroll ledger backfill** — `app:payroll:ledger-backfill` posts the accrual of runs approved, and the settlement of runs paid, before payroll started posting to the general ledger. Idempotent (the journal is keyed by source and source id); `--dry-run` lists what would be posted and `--cash` settles against caja instead of banco. The payment method of historical runs was never recorded, so settlements default to banco (1041). Lives in the Payroll context because Accounting must not depend on it.
- **SIRE — RCE (compras)** — `GET /api/v1/sire/rce?period=AAAAMM` descarga el ZIP «Reemplazar propuesta» del Registro de Compras Electrónico (libro 080400, 37 campos informados más los 4 finales vacíos, palote final, CRLF, ASCII), y `GET /api/v1/sire/rce/preview?period=AAAAMM` devuelve los registros, las compras excluidas (sin comprobante del proveedor; notas, que necesitan el comprobante que modifican) y las advertencias. Sale de las recepciones de mercadería contabilizadas: con IGV va a la pareja DG, sin IGV a «adquisiciones no gravadas»; la fecha de emisión es la de la recepción. Las facturas de proveedor de Cuentas por Pagar aún no entran porque no guardan base ni IGV. Pendiente contrastar con un archivo real aceptado por SUNAT.
- **SIRE — RVIE (ventas)** — `GET /api/v1/sire/rvie?period=AAAAMM` descarga el ZIP «Reemplazar propuesta» del Registro de Ventas e Ingresos Electrónico (libro 140400, 33 campos y palote final, CRLF, ASCII), y `GET /api/v1/sire/rvie/preview?period=AAAAMM` devuelve la cantidad de registros, los comprobantes excluidos (dados de baja) y las advertencias a revisar antes de presentar (componentes que no suman el total, notas sin comprobante modificado, facturas sin RUC, documentos sin líneas). Las bases se toman de las líneas por tipo de afectación (10 gravado, 20 exonerado, 30 inafecto, 40 exportación). Layout y reglas de formato portados de contaperu (MIT, ver `THIRD-PARTY-NOTICES.md`); pendiente contrastar con un archivo real aceptado por SUNAT. El RCE (compras) y la carga por API aún no existen.
- **Payroll accounting** — approving a payroll run now posts the accrual to the general ledger (remuneraciones 621, bonificación 622, EsSalud 627 against AFP 407, ONP 4032, quinta categoría 4017, EsSalud 4031 and remuneraciones por pagar 411), and paying it posts the settlement against caja (101) or banco (1041). `POST /payroll-runs/{id}/pay` accepts an optional `paymentMethodId` (CASH → caja, otherwise banco). The entry is posted before the status is committed, so a ledger rejection leaves the run unapproved. Migration `Version20261106000000_payroll_accounts` seeds the accounts; the PCGE mapping should be confirmed with the tenant's accountant. Runs approved before this change have no entry yet.
- **Despatch guides (GRE remitente)** — guides are validated on creation (series `T###`, transfer date, Catálogo 20 reason, recipient/carrier/driver documents, vehicle plate for private transport, ubigeos, weight, items) instead of failing at SUNAT. The "Otros" reason description and the originating invoice/boleta (`relDoc`) are now sent. A guide is only locked once SUNAT accepts it (CDR code 0 or 4000+); rejected or errored guides can be sent again.
- **Accounts-payable aging** — `GET /api/supplier-bills-aging?as_of=` returns open supplier-bill balances by days past due (not due / 1–30 / 31–60 / 61–90 / 90+) per supplier with currency totals and a bill-level detail; `GET /api/supplier-bills-aging/export?view=summary|detail` downloads it as XLSX (gated by `excel_export`). Cut-off dates in the past are rejected because balances are the current ones.
- **Build version in the UI** — the deployed semver tag now shows on the login screen (`.brand-version`) and in the app footer. Sourced from the `APP_VERSION` env var, set in the prod/staging image from the git tag (`build-image.yml` → Docker `ARG`/`ENV`); unset locally resolves to `dev`, which both surfaces hide. Replaces the half-wired `.version` file lookup in `SettingsExtension`.
- **"Imprimir logo en comprobantes" toggle** — `TenantSettings.printLogo` (writable via `PATCH /api/tenant/settings` all along, default on) now has a UI control: a new "Comprobantes" section in Configuración → General. It had no row in the generic `config` list and wasn't among the typed toggles, so a tenant could never turn the ticket/A4 logo off.
- **Sales report — "Ventas por método de pago (detallado)"** (`payment-method-breakdown`) — one row per comprobante in the range, a column per active payment method with the amount paid via that method, plus "Total pagado" / "Total comprobante", and a footer TOTALES row summing every method column. New `src/Sales/Report/PaymentMethodBreakdownReport.php` (tagged `app.sale_report`, pivots dynamically over `payment_method`), reachable from Consulta de ventas → report dropdown. Uses the existing `Nubit\Platform\Export\XlsExporter`; gated by the `excel_export` feature like the other exports.
- **Integration platform (`src/Integration`, ADR-017)** — a reusable machine-to-machine surface, validated by SUNAT emission for `nubit-control`'s own hosting sales:
  - **Tenant-scoped API keys** (`nb_<env>_<tenant>_<secret>`, SHA-256, revocable) behind a new `integration_api` firewall on `^/api/v1`; `app:integration:api-key:create`.
  - **`POST /api/v1/documents`** builds a CPE without a `Sale` (`SyntheticVoucherFactory` + an optional-`Voucher` seam on `BillCreateUseCase`/`BillSendUseCase`), idempotent on `external_id`, dispatched through the existing SUNAT pipeline; `GET /api/v1/documents/{reference}` for polling.
  - **Outbound webhooks** — transactional outbox (`IntegrationEvent`), HMAC signatures (`Nb-Signature`, Stripe-style), per-endpoint retries with dead-letter and auto-disable, `app:integration:webhooks:tick` (scheduled every minute) and `:replay`. Event catalog: `document.accepted` / `rejected` / `voided`.
  - **Settings UI** (Configuración → Integraciones) to manage API keys and webhook endpoints, with one-time secret reveal, a delivery log and manual retry, served by `src/Integration/Controller/Settings/*` under `perm:settings.edit`.
  - Migrations `Version20260830140000`–`160000` (per-tenant: `integration_api_client`/`_key`, `integration_document`, `integration_event`, `integration_webhook_endpoint`/`_delivery`).
- **POS settings** — New `auto_print` tenant setting and a "Punto de venta" section in Configuración → General with typed toggles for **Emitir boleta/factura por defecto** (`autoInvoice`) and **Impresión automática** (`autoPrint`). The POS now honours both as per-tenant defaults; the General tab is reachable by every tenant again (previously hidden for single-store tenants). Migration `Version20260828120000_tenant_settings_auto_print` (default on, no behaviour change for existing tenants).
- **SLICE-CP-02** — Granular role system for the control-plane admin panel: three roles (`ROLE_CP_VIEWER` ⊂ `ROLE_ADMIN` ⊂ `ROLE_SUPER_ADMIN`) with security hierarchy, `#[IsGranted]` guards on all controllers, and Twig `is_granted()` template guards. Destructive tenant actions require `ROLE_SUPER_ADMIN`.
- **SLICE-CP-01** — Login UI for the admin panel: `form_login` replaces `http_basic`, standalone Bootstrap 5.3 login page, CSRF protection, remember-me (7 days), brute-force throttling (5 req/min), and functional logout with session invalidation.
- **SLICE-CP-03** — Admin user management UI (ROLE_SUPER_ADMIN only): full CRUD via `AdminUserController` + `AdminUserRepository` (DBAL), password strength/confirm validation, AJAX active-toggle, and audit log for all operations.

### Changed
- **The POS back button only exists where it can go somewhere** — it used to run `navigate(-1)`, which for a cashier who lands on `/pos` after signing in leaves the app (or returns to the login). It now goes to a fixed destination (Inicio, else the first other entry of the user's menu) and is not shown at all when the POS is all the user can reach; their way out is "Mi perfil" / "Cerrar sesión" in the POS menu. The authorized menu moves out of the shell into a shared `useWorkspaceMenu` hook so the shell and the POS read the same destinations.
- **"Caja" moves into Finanzas as "Cajas y turnos"** — turn history, registers, categories and team control are supervision, so they sit next to "Cuentas de dinero" instead of being a sidebar entry of their own. It is shown to who supervises (`cash.manage`, `cash.close_any`, `cash.movement_any` or `treasury.view`) and to roles that cannot reach the POS; a cashier no longer sees it. The tab row stays visible on the page (it is one sidebar item, not four). Routes (`/cashbox/*`, `/cash-session/*`, `/cash-register/*`) and permissions are unchanged. Migration `Version20261123100000_cash_menu_into_finance` (tenants whose menu has no Finanzas group keep the old entry).
- **Price lists no longer use hand-written SQL** — `price_list_detail` is now the `PriceListItem` entity and the list editor, the `apply` endpoint and the server-side price check at sale time share one rule (`PriceListPricing`: special price, else base × factor, else base), which is what had drifted apart. No schema change.

### Fixed
- **"Cerrar caja" in the POS did not close the caja** — it only cleared a flag in `localStorage`; the session stayed open on the server and came back as open on the next reload, so the cashier believed the shift was closed with no count and no `cash_sessions` closure. It now opens the real closing (count, differences, server confirmation) and the POS is closed only when the server says so.
- **The POS said "Caja abierta" for a cashier with no session** — the flag defaulted to open and, when verifying, took any register open in the branch, even one opened by someone else, while a sale needs a session opened by the seller (`SALE_CASH_SESSION_REQUIRED`). The state now comes from the user's own session on the server (revalidated on focus and on reconnect, persisted for offline start with the other POS bootstrap queries) and shows "Verificando" until it answers.
- **A price change no longer re-prices a ticket in silence** — lines of the order in progress that follow the catalogue take the new price and the cashier is told which ones changed; a price typed by hand is kept. The cart is now reconciled against the whole catalogue at the customer's tariff, not against whatever the search filter shows (a changed price used to reach only the visible lines, and re-ran on every render).
- **Prices on the till stay current all shift** — the POS now refreshes the catalogue and the customer's price list when a product or price list changes (Mercure, within ~2 s), every 2 minutes as a backup while the tab is visible, and as soon as the tab regains focus or the connection returns. Saving a price list (written with SQL) now publishes the Mercure update that API Platform could not. A failed refresh keeps the prices on screen.
- **Price-list prices computed with a factor were refused at the till** — the server compared the submitted two-decimal price with the unrounded four-decimal tariff, so a cashier without `pos.price_override` was blocked on a legitimate price. The comparison now accepts the tariff at four decimals or rounded to two (`AuthorizedPrice`).
- **POS could sell at an outdated price** — the service worker answered `/api/products` and `/api/customers` with the previous cached copy (stale-while-revalidate) and only refreshed it for the next load, while the POS reads the catalog once per load. A till could therefore sell at a price changed days earlier, and keep it all shift. Both routes are now network-first (4 s timeout) and still fall back to the cache when offline.
- **Per-tenant feature override could not be saved** — `TenantFeatureOverrideManager::setOverride()` wrote an `updated_at` column that `tenant_feature_overrides` never had, so adding/editing an override from the control-plane Features tab failed with `SQLSTATE[42S22] Unknown column 'updated_at'`. The manager's unit test mocks the DB connection, so it slipped through.
- **Company logo missing from ticket/A4 PDFs** — `LogoProvider::embedded()` swallowed every storage read error with a bare `catch { return '' }`, so a logo that can't be read just vanishes with no trace. It now reads through `Nubit\Platform\Filesystem\FileManager` (the same service the media library uploads with, so the tenant prefix always matches) and logs a warning with the attempted path when the read fails.
- **Control-plane tables — empty band before the row-actions column** — `@nubitio/ui` sets `table-layout: fixed` on any DataTable with row actions, splitting leftover width equally across the data columns; tables with few/narrow columns (tenants, users) showed a wide gap before the sticky `···` cell. Overridden to `table-layout: auto` in the control-plane bundle.
- **Invoice quota is per calendar month again** — `TenantQuotaService` counted every quota resource with a lifetime `SELECT COUNT(*)`, so a plan's `invoices` allowance (free 500, basic 5000) was compared against the tenant's all-time `tax_document` count and never reset — a tenant that ever hit the number stayed blocked forever. `invoices` is now classified as a monthly quota in `TenantResourceCatalog` (`monthlyQuotaDateColumn`) and its usage — in both `check()`/`enforce()` and the control-plane Usage tab — is scoped to the current calendar month in `America/Lima` (resets on the 1st). `users`, `customers`, `products`, `branches`, `storage` stay lifetime caps. No data migration; over-limit tenants are unblocked automatically.
- **Control plane — "Cambios en las últimas 24 h" restored** — the tenant Usage tab lost its 24-hour delta table (comprobantes emitted, clientes/productos added, etc.) in the Twig→React migration even though the API kept returning `usageDeltas`. `UsageTab` renders it again (Recurso / Hace 24 h / Ahora / Cambio), the payment-quota row is labelled *mensual*, and `types.ts` now types `usageDeltas` correctly.
- **Fresh-tenant setup** — `InitialSetupService::configure()` no longer wraps the whole sequence in a manual outer transaction. That forced every nested `$em->flush()` (including `AuditTrailListener`'s second flush in `postFlush`) plus the seeders' own transactions into deep DBAL savepoints, which broke with `SQLSTATE[42000] 1305 SAVEPOINT DOCTRINE_2 does not exist` on a clean tenant DB — blocking `app:tenant:setup`, `app:demo:seed` and `POST /api/test/e2e/seed`. Each unit now manages its own transaction. CI never caught this because it provisions from a baseline dump with `configured = true`.
- **Dashboard — last-7-days chart** — `pickLast7SalesDays` matched sales rows by day-of-month across months, so early in a month it pulled the *current* month's future days (all zero) and emitted duplicate weekday labels, which collapsed the chart's category axis (tooltips read `S/ 0` on the real bar). It now only matches rows in the current month and derives labels from the actual date.

### Changed
- **Feature entitlements are code-defined** — `PlanFeatureManager::FEATURE_KEYS` (a 15-key constant) is replaced by `src/ControlPlane/Billing/Feature/FeatureCatalog.php`: one entry per key with label, category (*Comercial* / *Módulos ERP*), config flag and per-plan defaults (pattern: `PermissionCatalog`). A compiler pass (`RequireFeatureKeyPass`, wired in `src/Kernel.php`) fails the build if a `#[RequiresFeature]` / `hasFeature()` / `IS_GRANTED('FEATURE_…')` names an undeclared key. New `app:features:sync` reconciles `plan_features` to the catalogue (gap-fill; `--force` to reset) and runs after migrations — adding a feature no longer needs its own migration. The control-plane plan-features matrix and per-tenant override picker now list **all** keys grouped and operator-editable; `payroll`, `general_ledger`, `bank_reconciliation`, `fixed_assets`, `expense_reports`, `recurring_billing` were previously invisible. See ADR-013 amendment.
- **Dashboard rebuilt on Recharts** — the main dashboard (`/#/dashboard`) is now a fully-custom React + Recharts view (KPI row, 7-day sales bars, 12-month area trend, payment-method horizontal bars, breakdown tables) instead of the declarative `@nubitio/dashboard` config engine. Payment methods are shown as sorted horizontal bars rather than a donut. The "Hoy" block is folded into the dashboard as a slim attention strip (only items needing action), and the onboarding shortcuts only appear while tenant setup is incomplete. The data layer (`GET /api/bi/overview` → `mapEfactDashboardPayload`) is unchanged.
- **Modern SaaS restyle** — neutral near-black dark / off-white light theme tokens (killed the Tailwind-slate blue tint), softer low-contrast borders, flatter shadows (dropped the white inset ring in dark). Retouched the app shell (rounded inset sidebar items instead of full-bleed rows + 3px accent bar, softer header/panel dividers) and the user menu (neutral-grey hover, rounded inset items, roomier dropdown). Grid filter-row operator selector is neutral instead of an accent-tinted pill. Radii widened a step. Theme `--accent-color` fallback aligned to `@nubitio/ui`'s `DEFAULT_ACCENT` (`#1a6fd4`) — the running accent is still the per-tenant setting.

### Removed
- Orphaned legacy dashboard code superseded by the Recharts rebuild: `DashboardHero/Charts/Rankings/StatusBar/Operations`, `useDashboardMetrics`, and the `efactDashboardConfig` declarative config. `@nubitio/react-admin` now has no JS importers in the frontend (only its shared `style.css`).
